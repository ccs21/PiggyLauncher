# 제약을 우회한 구현 읽기

## 1. 실행 명령만 넘기면 충분하지 않은 이유

개발자는 여러 에뮬레이터에서 경로와 환경변수 방식을 시도한 뒤 임시 배치파일로 실행 조건을 맞추었다고 설명했다. `emulator_launcher.launch_game`에서 실행 대상과 ROM 경로를 준비하는 부분, 배치 내용을 만드는 부분, `monitor_emulator_and_bat`로 종료를 관찰하는 부분을 나눠 읽는다.

이는 Python이 외부 프로그램을 실행할 수 없어서 생긴 제약이 아니다. 호출하는 프로그램이 어떤 작업 폴더·인자·설정 파일을 기대하는지가 중요하다. 우회 방법은 호환성을 높이지만 임시파일 수명과 문자열 인용을 관리할 책임도 늘어난다.

실습: 실제 에뮬레이터 대신 인자와 작업 폴더를 임시 파일에 기록하는 작은 Python 프로그램을 만든다. 공백·한글을 포함하는 테스트 경로에서 직접 실행과 배치 실행 결과를 비교한다. 실제 ROM이나 시스템 폴더를 대상으로 하지 않는다.

## 2. 프로세스 종료와 게임 종료의 차이

일부 게임은 처음 실행된 프로세스를 종료하고 다른 프로세스로 다시 실행된다. 개발자는 이때 런처가 먼저 복귀하는 문제를 경험했다. `game_detail_screen.GameDetailScreen.run_game`, 내부 대기 함수, `wait_all`, `restore_launcher`를 따라 시작 단계와 종료 관찰을 구분한다.

대기 시간을 늘리는 것은 잘못된 복귀를 줄일 수 있지만 실제 종료 후 복귀도 느려질 수 있다. 이 문제를 Python 실행 속도의 문제로 설명하지 않는다. 감시 대상과 관찰 가능한 신호가 실제 게임 상태를 얼마나 잘 대표하는지의 문제다.

실습: 2초 실행 후 종료하는 테스트 프로세스와 잠시 뒤 다시 시작하는 테스트 프로세스로 두 경우를 재현한다. “한 번 실행된 프로세스가 사라짐”과 “다시 시작할 가능성까지 확인함”의 판정 차이를 기록한다. 2.0의 구현과 Classic의 현재 코드를 섞어 설명하지 않는다.

## 3. 작업 완료 시간과 화면 반응성

`register_thread`와 `register_progress_popup`을 같이 읽는다. 수집 작업을 수행하는 위치와 UI가 진행 신호를 받는 위치를 찾아 표시한다. 작업을 다른 스레드에 옮겨도 서버 응답 자체가 빨라지는 것은 아니다. 화면 이벤트를 처리할 기회를 확보하는 효과와 총 처리 시간을 따로 관찰한다.

실습: 외부 API 대신 일정 시간 후 가상 JSON을 반환하는 함수를 사용한다. 성공·오류·중단 각각에서 진행 상태가 어떻게 끝나야 하는지 먼저 적고, 신호와 화면을 연결한다. CPU 계산이 많은 작업에서도 같은 효과가 난다고 단정하지 않는다.

## 4. Python과 Windows 사이의 경계

`system_config_handler`의 상태 조회·적용·복구와 `main`의 화면 관련 Windows 호출을 읽는다. 외부 API 호출은 언어의 문법을 넘어 OS 자원을 변경한다. 성공 경로뿐 아니라 게임 실행 실패 시 원상복구 경로가 필요한 이유를 살핀다.

실습: 실제 설정 변경 함수를 가짜 함수로 바꿔 호출 순서를 기록한다. 적용 전 상태가 없는 경우, 적용 중 실패, 복구 중 실패를 구분한다. 실기기 변경은 이 순서가 검증된 뒤 별도로 수행한다.

## 5. 비밀정보를 숨기는 것과 분리하는 것

`scraper_credentials`에서 외부 API 자격 증명을 읽는 경계를 살핀다. 공개 프로그램 안에 고정 암호화 키를 함께 넣으면 사용자가 실행에 필요한 값을 다시 얻을 수 있다. 이 공개본은 서비스 비밀값을 제공하지 않고 각 학습자가 자신의 값을 설정한다.

로컬 JSON도 안전한 비밀 저장소는 아니다. 평문이라는 한계를 문서에 알리고 사용자 암호는 자동 저장에서 제외했다. 더 나아갈 실습은 OS 자격 증명 저장소 사용과 삭제·오류 처리를 설계하는 것이다. 암호화 알고리즘을 직접 만들어 해결하려고 하지 않는다.
