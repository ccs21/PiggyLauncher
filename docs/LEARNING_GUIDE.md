# 코드를 읽는 순서와 학습 자료

이 문서는 정리된 공개본을 읽는 길잡이다. 실제 파일 구성은 SOURCE_MAP.md, 각 함수 위치는 FUNCTION_INDEX.md에서 확인한다. 아래 실습 중 자동 검증한 범위는 REVIEW_RESULTS.md에 구분했다.

## 먼저 익힐 것

함수·클래스·딕셔너리·예외 처리·파일 읽기를 알고 시작하면 좋다. Qt 이벤트와 스레드는 해당 장에서 설명한다. 프로그램 전체를 처음부터 한 줄씩 읽기보다 한 동작의 입력과 출력을 따라간다.

| 순서 | 질문 | 대표 코드 | 실습과 확인 방법 |
|---|---|---|---|
| 1. 시작과 화면 | 실행하면 어떤 순서로 화면이 만들어지는가? | main.py, theme_manager.py, top_bar.py, central_content.py, bottom_bar.py | 임시 테마의 여백을 바꾸고 영향을 받는 위젯 찾기 |
| 2. 설정과 데이터 | 화면에서 바꾼 값은 어디에 저장되는가? | settings_popup.py, tab_launcher.py, category_select_popup.py | 가상 설정 JSON이 없거나 잘못됐을 때 기본값 처리 확인 |
| 3. 게임 등록 | 설치 정보와 화면용 정보를 어떻게 결합하는가? | steam_scanner.py, epic_scanner.py, gog_scanner.py, stove_scanner.py, register_thread.py | 가상 설치 정보로 등록 목록 생성, 중복 등록 확인 |
| 4. 수집과 작업 진행 | 네트워크 작업 중에도 화면은 어떻게 반응하는가? | steam_crawler.py, gog_crawler.py, cdp_scraper.py, register_progress_popup.py | 저장해 둔 가상 응답으로 성공·실패·부분 수집 재현 |
| 5. 실행과 복귀 | 프로세스 하나가 종료되면 게임도 종료된 것인가? | game_detail_screen.py, emulator_launcher.py | 테스트용 프로세스로 시작 실패·재기동·종료 시나리오 비교 |
| 6. 시스템 변경 | 게임 실행 전 변경한 설정을 어떻게 복구하는가? | system_config_handler.py, graphic_setting_popup.py, batch_setting_popup.py | OS 호출을 가짜 구현으로 바꾸어 적용·복구 순서 기록 |
| 7. ROM 관리 | 파일 경로·게임 정보·실행 코어는 어떻게 연결되는가? | rom_list_popup.py, rom_edit_popup.py, core_edit_popup.py, scraper_setting_popup.py | 임시 폴더의 가상 파일로 목록 수정과 경로 연결 확인 |
| 8. 입력과 알림 | 입력 이벤트와 대기 중 알림을 어떻게 관리하는가? | gamepad_handler.py, gamepad_manager.py, notification_manager.py | 가상 입력과 알림으로 포커스·일시정지·재개 순서 확인 |
| 9. 배포와 외부 연결 | 내 PC 밖에서도 재현하려면 무엇이 필요한가? | requirements-lock.txt, examples의 서버·업데이트 예제 | 깨끗한 환경에서 실행하고 네트워크가 끊긴 상황 확인 |

실습은 개인 게임·설정·회원 데이터 대신 임시 폴더와 가상 자료를 사용한다. 실제 해상도 변경이나 게임 실행이 필요한 실습은 부작용과 복구 방법부터 설명한다.

## 각 장의 공통 형식

1. 사용 중 어떤 문제가 생겼는가?
2. 관련 파일·함수와 호출 순서는 무엇인가?
3. 입력, 출력, 변경하는 상태는 무엇인가?
4. 현재 코드는 어떤 방식으로 해결하는가?
5. 이 방식이 실패할 수 있는 조건은 무엇인가?
6. 작은 수정 과제와 관찰할 결과는 무엇인가?

## 제약을 어떻게 우회했는가

[구현 사례](CASE_STUDIES.md)에서 제약·채택한 구현·비용과 한계·실습을 읽는다. 시도했던 방법은 개발자의 확인이 있는 경우에만 기록한다. Python 자체의 제약, Qt의 실행 규칙, Windows의 제어 방식, 외부 프로그램/API의 특성을 구분한다.

| 읽을 사례 | 구분할 제약 | 코드에서 추적할 해결 방법 | 함께 설명할 비용·한계 |
|---|---|---|---|
| 네트워크 작업 중 화면 반응 | UI 이벤트 루프와 동기 I/O | register_thread.py와 진행 화면 사이의 작업·신호 전달 | 스레드 생성만으로 취소·오류 처리·모든 계산 성능 문제가 해결되지는 않음 |
| Windows 기능 제어 | 운영체제 연동 | main.py의 ctypes/win32 호출, system_config_handler.py의 시스템 설정 처리 | Windows 의존성, 실패 처리, 변경 전 상태 보관 및 복구 |
| 실행 명령과 작업 폴더 | 외부 실행기의 인자·경로 요구 | emulator_launcher.py의 프로세스 실행과 임시 배치파일 흐름 | 따옴표·공백·인코딩·임시파일 수명·실행 실패 |
| 게임의 재기동 | 외부 프로세스 수명과 실제 게임 상태의 차이 | game_detail_screen.py의 시작·종료 관찰과 복귀 처리 | 성급한 종료 판정과 복귀 지연 사이의 선택 |
| 웹사이트에서 정보 수집 | 외부 서비스와 인증·페이지 구조 | cdp_scraper.py 및 플랫폼별 수집 코드 | 브라우저 비용, 사이트 변경, 세션·개인정보 취급 |
| Python 코드의 EXE 배포 | 실행 환경과 리소스 포함 | 검토할 PyInstaller 빌드 설정 | 외부 파일 포함, 경로 차이, 의존성 라이선스, 깨끗한 환경에서 재검증 |

이 표는 조사 항목이며 각 구현의 성능이나 안정성을 검증했다는 뜻은 아니다. 실제 함수와 실행 결과를 확인한 뒤 사례를 완성한다.

### 피해야 할 설명

- “Python은 느리므로 스레드를 쓰면 빨라진다”처럼 원인과 효과를 뭉뚱그리지 않는다. 처리 시간과 UI 응답성을 따로 관찰한다.
- “Python으로는 실행할 수 없어 BAT를 썼다”라고 단정하지 않는다. 실행기별 요구와 당시 재현한 문제를 설명한다.
- 메모리 사용량을 줄이지 못한 원인을 확인하지 않고 언어 탓으로 돌리지 않는다. 이미지·브라우저·UI·캐시 등 무엇을 측정했는지 기록한다.
- 외부 실행 파일에 위임한 기능은 그 구성요소의 역할도 설명한다. 순수 Python으로 모두 구현한 것처럼 적지 않는다.

### 사례 작성 양식

1. **목표:** 사용자가 어떤 동작을 기대했는가?
2. **증상과 재현 조건:** 어떤 환경에서 무엇이 실패했는가?
3. **제약의 출처:** 언어/런타임, 라이브러리, OS, 외부 프로그램 중 어디인가?
4. **시도와 선택:** 확인된 시도 및 현재 방법을 선택한 이유.
5. **코드 흐름:** 함수 호출, 데이터 전달, 프로세스·스레드 경계.
6. **검증:** 성공뿐 아니라 실패·중단·재실행에서 확인할 결과.
7. **대가:** 복잡성, 자원 사용, 플랫폼 의존성, 남은 실패 조건.
8. **확장 과제:** 다른 접근을 실험하고 같은 조건에서 비교하기.

## 먼저 작성할 사례

### 게임이 꺼졌는데 아직 끝나지 않은 경우

개발자 설명에 따르면 일부 게임은 실행 직후 종료되었다가 다시 시작한다. 이 경험을 출발점으로 game_detail_screen.py의 run_game, wait_all, restore_launcher 및 감시 관련 함수를 추적한다. 대기 시간의 정확한 값과 판정 흐름은 해당 코드를 검토한 뒤 기록한다. 2.0에서 사용한 개선 방식을 Classic에 이미 구현된 기능처럼 설명하지 않는다.

### 에뮬레이터를 실행하는 데 배치파일을 사용한 이유

개발자는 절대경로와 환경변수 등을 시도한 뒤 호환성 문제 때문에 임시 배치파일 방식을 채택했다고 설명했다. emulator_launcher.py의 launch_game, monitor_emulator_and_bat, launch_bat_after_delay를 읽으며 실행 경로·작업 폴더·인자·임시파일 정리를 나눠 살핀다. 모든 에뮬레이터에서 배치파일이 필수라는 결론으로 일반화하지 않는다.

### 알림을 바로 표시할 수 없는 경우

notification_manager.py의 push → _try_show_next → _on_popup_closed와 pause/resume을 따라 큐와 화면 표시의 관계를 배운다. 외부 서비스 호출 없이 가상 알림으로 재현한다.

## 자료 선택 기준

- 실제 사용된 구현: 의존성·민감정보·라이선스를 검토한 뒤 정리해서 포함.
- 시행착오: 개발자가 확인한 배경을 문서로 보존. 복사본 소스 전체를 첨부하지 않음.
- 사용하지 않는 코드: 동적 호출과 별도 실행 여부를 확인한 뒤 제외.
- 테스트: 원본 개인정보를 사용하지 않는 것으로 선별하고 필요한 사례를 추가.
- 운영 서버·관리 도구·후원·광고 자료: 제외.
- 서버 학습: 운영 구현을 옮기지 않고 독립 예제를 새로 작성.
- 리소스: 직접 제작했거나 재배포 조건을 확인한 파일만 포함.
