# 3. 공지 서버와 지속 큐

오프라인 동안 세 건이 등록되면 최신 한 건 조회로 나머지 두 건을 복구할 수 없다. 교재는 단조 증가 sequence와 after 커서로 목록을 읽는다. 같은 시각의 공지도 구별한다.

## 공지 작성

프로젝트 루트에서 실행한다.

```powershell
& $python examples/notice_store.py --add '첫 실습 공지'
& $python examples/notice_store.py --add '둘째 실습 공지'
& $python examples/notice_store.py --list
$env:LAB_NOTICE_DB = 'lab_data/notices.sqlite'
& $python examples/lab_server.py
```

LAB_PASSWORD도 1장처럼 설정한다. SQLite의 lab_bulletins(sequence,text)는 이 교재가 새로 만든 테이블이다. 실제 제품의 DB를 사용하지 않는다. LAB_NOTICE_DB가 없으면 서버는 메모리 가상 공지 두 건을 사용한다.

작성 권한은 로컬 파일 접근 권한으로 제한한다. 웹 작성 API는 없다. 관리자 웹 화면을 추가하려면 별도 관리자 인증·권한 검사·입력 검증·감사 기록이 필요하다.

## 페이지 조회

```powershell
curl.exe 'http://127.0.0.1:8000/lab/notices?after=0&limit=1'
```

첫 응답은 items 한 건, next_after=1, has_more=true다. 다음 요청은 after=1이다. has_more=false까지 순차 조회한다. limit는 1~100이다. SQL 값은 문자열 보간 대신 매개변수로 바인딩한다. [SQLite 문서](https://docs.python.org/3.10/library/sqlite3.html)

## 재시작·오프라인 실험

둘째 터미널에서:

```powershell
& $python examples/notice_sync.py
& $python examples/notice_sync.py
```

첫 실행에는 공지가 표시되고, 같은 DB를 대상으로 한 둘째 실행에는 새 공지가 없으면 출력되지 않는다. 커서와 미표시 큐를 lab_data/inbox.local.json에 함께 저장한다. 서버를 끄고 CLI로 새 공지를 추가한 후 다시 켜면 추가 공지를 받는다. 연결 실패 시 저장된 상태는 유지된다.

화면 표시 직후 확인 저장 전에 전원이 꺼지면 다음 실행에서 중복 표시될 수 있다. 커서만 먼저 저장해 공지를 유실하는 것보다 중복을 허용하는 설계다. 정확히 한 번 표시를 보장하지 않는다. 한 프로세스만 같은 큐 파일을 사용해야 한다.

읽을 코드:

- [notice_store.py](../examples/notice_store.py): 연결 수명, 트랜잭션, limit+1 조회.
- [notice_sync.py](../examples/notice_sync.py): 페이지 진행 검사, 커서와 큐의 원자적 파일 교체.
- [notification_manager.py](../notification_manager.py): 수신과 Qt 표시의 분리.

DB를 과거 사본으로 복원하면 클라이언트 커서가 앞설 수 있다. 실제 운영에는 서버 세대 ID 또는 명시적 재동기화 정책을 추가한다. 무조건 커서를 0으로 바꾸면 과거 알림이 모두 다시 뜬다.
